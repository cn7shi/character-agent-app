# 设计与实现决策记录

这里记录影响后续维护的选择。局部实现理由同时放在代码旁；阶段报告记录实际完成与验证结果。日期为 2026 年 10 月 5 日。

## D01 两端数据通过接口对齐

问题：原生页面需要快速读取和离线查看，服务端需要管理账号内的完整记录。

选择：客户端使用 Room 管理本地数据，服务端使用独立数据库，通过 API 对齐。实体、传输对象与界面状态分开。

原因：避免页面依赖服务端表结构，也避免更换主题或存储实现时重写聊天业务。

代价与复评：需要明确的同步状态和去重逻辑。增加编辑、删除、多设备写入时补充版本冲突与删除标记规则。当前仅实现服务端基础，Room 尚未落地。

## D02 后端采用模块化单体与 SQLite

问题：目前需要验证角色和独立会话，不需要复杂部署。

选择：FastAPI 负责 HTTP，应用层组织业务，仓库接口隔离 SQLite。开发服务使用单进程和本项目独立数据库。

原因：能较早得到可运行结果，后续模型、工具与 MCP 可通过适配接入。相较直接复制原型路由中的 SQL，更容易验证用户范围与事务。

代价与复评：SQLite 同时只有一个写事务，本阶段只面向本机开发。多实例或写入竞争明显时评估 PostgreSQL，并验证迁移和并发行为。

## D03 会话创建与去重记录在同一事务提交

问题：网络重试和并发点击可能产生重复会话；只先查询再插入不能防止竞争。

选择：用 `BEGIN IMMEDIATE` 在查询请求记录前取得写事务，原子写入会话和去重记录；请求键按用户与操作类型唯一。相同规范化请求返回原会话，不同内容返回 409。

原因：对并发重试给出确定结果，也避免出现会话写入成功但去重记录未保存的中间状态。

代价与复评：写操作被短暂串行化。事务内只做数据库工作，不调用模型或网络。迁移到其他数据库时重新实现并验证相同语义。见 `SqliteCatalogRepository.create_conversation`。

## D04 会话固定人设版本

问题：角色资料更新后，已有会话的人设可能突然改变。

选择：新会话引用当时已发布的不可变设定版本，数据库用角色与版本的组合外键约束其归属。

原因：保证后续上下文构建可解释，角色资料变更不会无声改变已有会话。

代价与复评：需要保留旧版本。后续若允许会话主动升级人设，应设计明确的升级操作。本阶段只有预置版本，没有角色编辑接口。

## D05 使用有范围的游标分页

问题：普通页码在会话更新时容易跳动，客户端也不能把一个用户或列表的游标用于另一个范围。

选择：按稳定字段和 ID 排序，游标签名包含列表类型、用户与位置；签名密钥保存在运行目录，重启后继续有效。

原因：防止意外篡改或跨范围复用，使分页位置可验证。身份检查仍独立执行，游标签名不替代访问控制。

代价与复评：会话更新时间变化时列表可能重复，客户端按 ID 合并；尚不提供跨请求的快照一致性。需要导出稳定快照时另行设计。

## D06 开发身份显式开启且仅限本机

问题：需要两个用户验证隔离，但正式登录方案尚未确定。

选择：仅在显式开发模式下生成两个随机访问凭证，保存在忽略提交的运行目录；启动脚本固定监听回环地址并关闭代理头推断。默认模式拒绝开发身份。

原因：现在即可验证真正的用户范围，避免在业务函数中依赖固定的全局用户。

代价与复评：当前服务不具备正式注册登录和对外部署能力。身份解析器独立，接入正式认证时替换并保留隔离测试。开发凭证不输出到日志或提交到源码。

## D07 消息与执行功能分阶段落地

问题：阶段 2 需要让客户端知道空会话如何查询，但消息、任务、取消和事件流需要额外的事务设计。

选择：阶段 2 的消息查询先验证会话归属，再返回空列表。未提供创建消息或执行任务接口，也未创建相应表。阶段 3 再增加迁移与完整行为。

原因：保留可用的小阶段，避免用模拟历史掩盖尚未实现的能力。已导出的 OpenAPI 只包含实际实现的操作。

代价与复评：阶段 2 当时不能聊天。阶段 3 已替换空消息查询并验证真实保存、去重、取消和事件恢复，保留此记录说明分阶段选择。

## D08 数据库连接显式关闭

问题：Python 的 SQLite 连接上下文管理器处理事务，不负责关闭连接；Windows 下未关闭连接会阻止删除临时数据库。

选择：数据库适配器统一使用 `try/finally` 关闭连接，测试也复用该连接管理入口。

原因：第一次并发验证发现测试检查代码残留了连接，清理临时数据库失败。显式关闭使生产代码与验证代码都能确定释放资源。

代价与复评：当前每个操作建立短连接。将来引入连接池时继续维持同样的事务与资源释放约定。

## D09 消息、任务和事件原子提交

问题：消息内容已更新而事件未保存，会让断流后的客户端缺少一部分回复；重复提交也可能生成两次。

选择：创建任务时，把消息、回复占位、任务、去重记录和首个事件放进同一事务。每次更新或终止都同时保存消息状态和事件。数据库限制同会话只能有一个活动任务，并约束消息与任务的用户和会话一致。

原因：客户端只能观察到完整提交的状态，重试返回原任务，重连可从数据库按序号补读。完整快照通过消息 ID 替换，重复事件不会重复拼接文本。

代价与复评：完整快照占用更多空间，写入按 SQLite 短事务串行。模型输出频繁或历史增长后，评估事件合并、快照加增量与裁剪，并重新验证恢复边界。

## D10 生成独立于 HTTP 与订阅连接

问题：提交请求的客户端可能在响应返回前离线，事件订阅也会随页面退出而中断。

选择：后台定期读取数据库里的排队任务，HTTP 只负责受理；订阅从持久事件读取，不拥有模型任务。取消先保存意图，再通知正在等待模型的协程。

原因：请求断开不丢失已受理工作，也不会把页面退出误当作取消。数据库线程中的提交不被直接取消，避免线程继续写入而协程已经释放会话。

代价与复评：当前后台调度器在单进程内，最多 8 个并行任务，排队没有生产配额。正式部署时增加认证、配额、可靠队列和监控；真实模型适配必须能在取消时释放网络连接。

## D11 单执行器锁与保守恢复

问题：服务重启后不知道原模型是否已完成；两个进程同时启动恢复可能把对方的活动任务标记失败。

选择：通过操作系统文件锁限制一个数据目录只运行一个开发执行器。获取锁后，将遗留非终态任务及输出标记失败，记录 `RUN_INTERRUPTED`，保留部分文本，不自动重试模型。

原因：恢复状态可以明确说明发生了中断；自动重放未来可能有付费或写入副作用的调用不可靠。进程退出后由操作系统释放锁。

代价与复评：当前不支持多进程扩展，崩溃后需要用户明确发起新任务。引入分布式队列后改为带租约的执行所有权和逐步恢复，不能直接删锁再加多个工作进程。

## D12 模型边界、上下文与模拟标记

问题：模型供应商会变化，阶段 3 需要验证业务链路，但不应把拼接文本展示成真实 AI 回答。

选择：领域定义 `TextModel` 与独立上下文，模型实现放在适配层。阶段 3 取最近 20 条已完成消息；阶段 4A 改为最近 10 个完整成功轮次加当前消息，并按 48000 字符限制移除完整旧轮次，避免截出以助手开头的半轮对话。失败或取消的轮次不参与下一次生成。任务保存 `model_name`、`is_simulated`，模拟文本也有明确标记。

原因：替换供应商不需要改 API、消息表或主题；上下文范围可验证，部分失败输出不会被当成完整对话。供应商异常只转成可展示的错误，不向客户端转发内部异常文本。

代价与复评：此阶段没有 Agent 循环、长期记忆或 token 预算；阶段 5 的有限工具循环见 D15。接入真实模型时按供应商要求处理完整轮次、上下文预算、超时和工具调用；不能用当前模拟测试代替真实服务验证。

## D13 凭证与 Git 历史分开保护

问题：用户要求真实模型密钥不要进入 Git；仅添加 `.gitignore` 无法处理强制添加或已经提交的敏感内容。

选择：模型配置使用被忽略的 `model.local.json` 或环境变量，示例密钥为空。提交前扫描暂存区实际内容，推送前扫描分支可达历史。模型密钥使用 `SecretStr`；启动校验隐藏原始输入，运行期间日志对当前密钥脱敏，供应商错误转为固定安全错误。

原因：分别覆盖误添加文件、把密钥写进普通文件、只清理工作区、只删除最新提交中的密钥、错误回显等路径。Android 与业务 API 不接收供应商凭证。扫描输出只含文件名和问题类别。

代价与复评：本机 JSON 为明文，扫描规则不是所有密钥的识别保证，Git 钩子也不是远程强制策略。正式部署引入密钥管理、访问权限与服务端检查；历史增长后优化 Git 对象扫描。已泄露凭证需要先撤销或轮换。

## D14 先支持明确范围的兼容文本协议

问题：用户希望先支持 OpenAI 兼容接口，稍后再选服务，不能据此假定特定供应商行为或调用真实付费服务。

选择：实现 Chat Completions 文本 SSE 适配，配置 API 基址、模型名称、密钥、生成时限和输出参数。默认 `mock`。必须收到 `finish_reason: stop` 与 `[DONE]` 才完成；截断、断流、过滤和不支持的工具调用都保留部分文本并标记失败。

原因：保持现有业务协议不变，供应商细节集中在模型适配器。不同服务的兼容程度需要实际验证；不能把 TCP 正常关闭直接当作完整回答。

代价与复评：当前不覆盖 Responses、多模态或工具调用。模型 HTTP 客户端不自动重试 POST、不跟随重定向、不隐式使用代理和 netrc，避免重复计费或意外改变凭证发送目标。取消会关闭本机连接，不承诺供应商停止计算或计费。确定服务后验证参数、终止语义与 token 预算，再按需要增加明确适配。

接口格式核对：[Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)、[流式事件](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)。连接生命周期参考 [HTTPX 异步流](https://www.python-httpx.org/async/)。

## D15 固定回复与有限工具循环让开发不依赖 AI 配置

问题：用户希望真实模型稍后配置，先推进聊天页面与角色能力；仅返回“已保存”台词不能验证工具流程。

选择：默认模拟器提供两条固定回复和明确的“记笔记”规则。模型边界可输出结构化 `ToolRequest`，执行器通过注册表调用工具，把真实结果回传后再生成回复；限制 3 次工具轮次加 1 次回复轮次，沿用整体时限与文本上限。

原因：页面、存储、权限、事件和取消都可以独立联调。模型文本不能冒充工具成功，重复规划也无法无限运行；将来替换规划器时继续复用工具接口。

代价与复评：规则不是自然语言理解，所有模拟回复保留标记；兼容模型当前仍只支持文本。接入真实工具调用时需验证参数增量解析、调用标识与工具结果协议，MCP 等慢速外部工具需要另外设计时限和取消。

## D16 本地工具产物与结果原子保存

问题：笔记写入后如果结果丢失，重试会创建重复笔记；取消或崩溃可能让页面误判执行结果。

选择：本地笔记、工具成功记录和事件在同一短事务提交；调用唯一键为 `(run_id, call_id)`，保存原始请求指纹。重复请求返回已保存成功或失败记录，同键不同内容报冲突。取消与写操作使用同一数据库串行化，已经提交的笔记保留；服务恢复不自动重放工具。

原因：数据库中的真实产物和结果保持一致。事务失败不会留下成功事件，记录失败时不回显 SQL 或未经校验的参数；回复生成失败也不抹去已经完成的工具结果。

代价与复评：当前只适用于本地数据库短操作，开始和成功事件同时提交，没有独立持久的执行中状态。MCP 或其他外部写入无法随本地事务回滚，接入时必须增加执行中、结果不明、外部去重与核对策略，不能直接复用本地异常重试方式。

## D17 人设版本同时固定能力权限

问题：开启笔记工具后，旧会话不应在用户不知情时获得更多能力；模型参数也不能决定数据属于哪个账号。

选择：为林舟发布允许 `notes.save` 的版本 2，新会话引用新版本，已有版本 1 会话不变，星禾暂不开放工具。实际执行在数据库内重新读取会话版本权限，用户与会话范围从已认证任务取得；工具参数只接受标题和正文。

原因：能力变化与人设变化使用同一可解释的版本边界。即使规划器提出未授权工具或伪造用户编号，也不能越过服务端权限和归属检查。

代价与复评：体验新工具需要创建支持该能力的会话。以后若允许旧会话升级、用户授权工具或角色编辑，需要明确的升级与撤权流程；当前尚未提供这些接口。

## D18 Android 先建立可构建的业务与展示边界

问题：原有 Android 目录只有职责说明，需要在不依赖真实模型的情况下实现页面和本地数据。

选择：启用 app、domain、network、data、designsystem 与四个 feature 模块。domain 定义纯 Kotlin 模型、仓库和后端网关接口；Room 保存带连接范围的查询快照及待发送记录，页面只读领域对象，JSON 映射留在 data 内。采用本机已有的 AGP 9.3.2/Gradle 9.5.0 组合，使用内置 Kotlin；Room 用 KSP 生成实现并导出 schema。

原因：模块依赖能在编译时检查，界面不会直接操作 SQL 或供应商协议。开发初期使用独立的本地快照格式足以验证离线读取，不需要把后端表复制到手机。固定依赖和 Wrapper 校验使新环境构建更可重复。

代价与复评：快照正文采用 data 层内部 JSON，当前不支持复杂本地搜索、局部字段更新和大规模历史分页；需要这些能力时迁移为细化的 Room 表并提供 schema 迁移，不能使用破坏性重建丢弃待发送记录。尚未使用的设备 Agent、模型与 MCP 模块继续保留目录。

版本与编译依据：[AGP 9.3](https://developer.android.com/build/releases/agp-9-3-0-release-notes)、[内置 Kotlin](https://developer.android.com/build/migrate-to-built-in-kotlin)、[Room](https://developer.android.com/jetpack/androidx/releases/room)、[KSP](https://github.com/google/ksp/releases)。

## D19 开发连接独立于模型密钥，并隔离本地缓存

问题：Android 需要访问开发后端，但不能把本机访问凭证放进 APK，也不能在更换连接后展示上一连接的数据。

选择：在设置页输入后端地址和访问凭证，使用 Android Keystore AES-GCM 加密保存，不进入 Room、源码、构建参数和日志。缓存范围由规范化地址与高熵凭证的 SHA-256 指纹生成。切换连接取消旧会话观察并清空界面状态；禁用备份。开发 HTTP 只允许 127.0.0.1 与 10.0.2.2，其他地址要求 HTTPS；HTTP 不自动重试 POST 或跟随重定向。

原因：开发凭证无需伴随源码分发，模型密钥继续只留在后端；不同服务和身份不能共享同一份本地缓存。原始网络异常不直接展示给用户。

代价与复评：凭证轮换后暂时产生新缓存范围，旧缓存保留但不可从其他连接页面读取；这不是正式账号系统。正式认证后改用验证过的稳定用户 ID，增加登出数据策略、过期处理与凭证轮换。Keystore 和输入法表现必须在设备上验证。

## D20 发起写请求前先保存重试身份

问题：手机发出消息或创建会话后可能没有收到响应，此时更换请求键重试会创建第二次执行。

选择：Room 先保存消息 ID、请求键和原始内容，再发 HTTP；创建会话也保存独立请求键。成功返回后把消息、任务快照与待发送项删除放进同一事务。未知受理结果只能重试原键，明确拒绝后才允许移除待发送项。

原因：进程重启后仍能继续同一次操作。模拟回复和真实模型都遵守相同的服务端去重规则，不需要 UI 根据文本猜测是否发送成功。

代价与复评：当前同会话只能保留一个待发送项，重试由用户触发，不实现后台自动发送。正式离线队列需要区分凭证过期、可恢复冲突与用户编辑，并增加 WorkManager 和队列调度验证。

## D21 Android 接入拆成快照验证与事件恢复两步

问题：一次加入原生工程、持久缓存、界面、SSE 和设备验证会让阶段过大，故障也难定位。

选择：阶段 6A 先用现有任务查询接口，每秒观察活动任务快照，网络失败延长间隔；离开页面或后台暂停观察，只有明确停止操作才取消服务端执行。消息与任务在同一 Room 事务保存，按服务端事件序号拒绝旧快照。阶段 6B 再加入 SSE、事件序号事务和设备验收。

原因：先证明同一套原生仓库能与后端完成聊天和真实笔记保存，以及响应丢失后的去重。查询和事件订阅都能复用领域状态，后续通信替换无需改页面。

代价与复评：目前回复刷新最多有约一秒延迟，不能声称 Android SSE 已完成；轮询增加查询开销。接入 SSE 时验证断流重连、重复事件和取消，并保留查询快照作为恢复方式。阶段 6 只有设备验证通过后才整体完成。

## D22 以业务适配器承载可拔插，共享有边界的可靠性策略

问题：6A 的 Transport 仍带 HTTP 方法、路径和 JSON 参数；只替换 HTTP 客户端并不能让业务脱离协议。页面组装也固定为一种连接。

选择：domain 增加 BackendAdapter、RunEvent、FailureKind，显式声明事件能力和关闭生命周期。HttpRequests/HttpEvents 只负责 HTTP 机制；HttpBackend 转换业务对象，BackendFactory 组装已集成实现。设置可选实时连接或兼容轮询，选择持久保存；两者使用同一缓存身份。ReliableBackend 统一对读取及已明确幂等的创建/取消操作重试。

原因：未来增加其他协议时实现业务适配器并在组装点注册，仓库和页面继续复用。默认每次操作最多 3 次尝试、25 秒总时限；指数退避带随机抖动，遵守 Retry-After，超过等待预算直接保留失败，不提前重试。未认证、无权限、冲突、格式不符等不会自动重试。HTTP 底层不盲目重试任意 POST。

代价与复评：当前实际协议是 HTTP 请求 + SSE，兼容模式是 HTTP 查询；内存模拟适配器只用于测试。不是动态下载插件，也未实现 WebSocket/gRPC/MCP 网络入口。正式接入新协议时必须满足同一业务契约、声明能力，并保证服务端幂等语义。页面及主题不参与传输实现。

## D23 内容和恢复位置共用一份事务，事件失败回退完整快照

问题：只保存游标可能丢正文，只保存正文可能重放；断流、缺号和错误终止不能被当成回复完成。

选择：沿用 schema 1 的 Run.sequence（内部 JSON 为 last_event_sequence）作为已提交游标，把回复、任务状态和序号放在同一 Room 事务，不另建可能失配的游标表。重复/旧事件忽略；缺号或未知类型查询完整快照，确认覆盖该序号后保存。断流先退避、核对快照，最多 3 次流连接后切换每秒查询；认证/权限错误直接停止。查询本身重试耗尽后停止观察并提供“重新连接”。

原因：服务端的快照、状态与事件序号本身就是同一事务的数据，可以补全内容；EOF 只表示连接关闭。终态立即停止订阅，不能依赖服务端关闭连接。观察离开前台时取消协程与套接字，返回前台重新读取持久快照；只有用户点“停止”才取消服务端任务。切换连接会关闭旧适配器，并防止旧界面任务覆盖新连接状态。

代价与复评：客户端目前不存工具调用明细，TOOL 事件只推进任务游标；笔记在进入会话、任务完成和进入笔记页时从真实记录核对，不根据模型台词认定成功。若增加工具过程页，需要专用投影和迁移。重连次数按一次任务观察计，不因收到少量数据就清零；前台重新进入可重新尝试。没有后台自动执行、永久重连或生产环境熔断器。

SSE 分帧依据：[WHATWG Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)。支持 UTF-8、BOM、LF/CRLF/CR、注释和多行 data；不完整帧不确认，单帧上限 512 KiB，队列上限 16 帧。HTTP 正文上限 4 MiB。连接 10 秒超时，普通调用整体 20 秒/读取空闲 15 秒；SSE 空闲 35 秒，覆盖服务端 15 秒心跳，不设置整个回复的网络调用时限。

## D24 结果不明与“当前不能重试”分别处理

问题：2xx 响应损坏、响应丢失、进程退出，甚至之后的凭证失效，都不能证明第一次发送未被受理；把“不自动重试”一概视为“可以移除”可能触发重复任务。

选择：发送前持久标记“正在确认”，重试始终沿用原消息 ID、请求键与正文。只有首次尝试被明确拒绝才能移除；一次自动重试中发生过结果不明，或手动重试旧待发送项时，后续拒绝也不能把它改成可丢弃。恢复旧版本留下的空错误字段同样按结果不明处理。

原因：自动重试策略知道本轮是否发生过不明结果，Room 则跨进程保存这一边界。这样连接中断与授权变化不会把原请求变成一次新的生成。

代价与复评：保守处理可能让一个实际上未受理的待发送项暂时保留。正式账号、服务数据迁移或凭证轮换接入后，需要服务端可查的请求回执及用户可理解的核对流程；不能为了清理界面随意丢弃原身份。当前凭证变化依旧产生独立缓存范围。

## D25 草稿、任务监听和资源关闭分别遵守自己的生命周期

问题：OpenCodeReview 委托审查发现，连接模式切换会清空同一身份的草稿；旧发送结果会清掉后续输入；本地已取消的任务可能仍占用静默事件流；退出时仅请求协程取消就关闭 Room，查询可能尚未结束。

选择：草稿按连接范围和会话保留，每次编辑生成独立对象，只有本次提交已确认或产生新待发送项，且输入仍是该对象时才清空。任务观察改为监听 Room 中活动任务 ID，变化时取消旧观察，正文更新不重建连接。所有连接会话归属同一个 ViewModel 父任务，退出取消所有子任务，全部完成后才关闭 Room。

原因：切换通信方式不改变身份；相同文本也可能是用户新输入，历史文本不能作为本次受理凭据。数据库终态比网络是否关闭更可靠。协程取消是异步过程，旧连接切换后仍在收尾的工作也必须先退出，不能与数据库关闭竞争。

代价与复评：草稿仍在内存中，进程重启恢复和 schema 迁移留待 6B2。资源关闭依赖适配器正确响应取消；将来接入阻塞式 SDK 时要另行验证。新增内部依赖注入入口和 ConnectionStore，使测试使用独立 Room、可控网络及内存配置；生产仍使用原 Android 工厂入口和 Keystore。测试不证明设备上的 Keystore 或系统生命周期已验收。

## D26 草稿独立落库，并与待发送区原子交接

问题：内存草稿无法跨进程恢复；异步保存可能在发送后写回旧文字，普通文本比较也无法区分重新输入的相同内容。数据库升级还必须保留未确认请求的原始身份。

选择：Room schema 2 新增 drafts，以 `(scope, conversationId)` 为主键，保存原文和每次编辑的随机 revision。使用从已提交 schema 1/2 生成的增量迁移，不启用破坏性重建。领域仓库提供草稿读写，页面不访问 Room。所有本地编辑经过单一写入协程；每个会话最多排队一个保存命令，快速编辑合并为最新值，发送前等待先前的保存命令完成。

选择：插入 outbox 与按 revision 删除对应草稿放在同一个事务，再发 HTTP。新版输入使用新 revision，旧请求不会删掉它。每次打开会话重新核对本地草稿，防止模式切换时恢复已经被待发送区接管的内存副本；读取期间暂缓编辑。保存失败保留输入并显示重试，普通退出先结束网络任务、排空本地保存，再关闭 Room。

原因：未发送内容属于手机和会话，不需要上传或依赖模型。原文保留空格、换行和表情，仅提交时按原协议校验和规范化。事务失败保留草稿且不留下半条待发送记录；成功交接后，即使进程退出或响应丢失，也沿用 outbox 的原消息 ID 和请求键。只修改颜色、布局或通信方式不改变这些规则。

代价与复评：仅承诺恢复已成功写入本机的内容，操作系统强杀或断电时仍在保存中的最后一次编辑可能丢失；界面区分保存中、已保存和失败。普通断开清除凭证及内存显示，已保存草稿跟随隔离缓存保留，重新连接同一身份可恢复；没有跨设备同步或缓存清理功能。当前同一进程只有一个 ViewModel 写入者，未来多窗口、多进程或跨设备草稿需要额外冲突规则。

迁移依据：[Android Room 数据库迁移与 schema 保留](https://developer.android.com/training/data-storage/room/migrating-db-versions)。本项目继续使用已固定的 Room 2.8.5，未因文档版本变化升级依赖；测试从仓库中的真实 schema 1 建库，再由生产数据库类升级，既核验结构，也核验旧数据。

## D27 用独立应用和真实设备检查恢复，而不让测试改动日常数据

问题：本机单元测试不能证明 Android Keystore、实际 Compose 页面、旋转和进程重启在设备上正常。联调若清空正常开发包或使用已有模型配置，又可能破坏日常数据或产生模型费用。

选择：新增 `deviceCheck` 构建类型，复用生产源码和调试网络配置，包名追加 `.devicecheck`。主机脚本必须显式指定设备；仅在校验测试标记后重置这个专用包。每轮新建模拟后端和两套临时身份，凭证经标准输入进入应用私有文件，测试输出先脱敏，截图仅取聊天和笔记页。结束后删除引导配置、关闭本轮服务、移除本轮创建的端口转发，并把清理失败计入失败结果。

选择：Compose 设备测试通过真实设置、发送、主题和身份切换入口操作；各检查点之间调用 Android 强制停止。断网通过停止隔离后端并确认端口不可连接实现，恢复使用同一后端数据库；核验原消息 ID 和请求键重放返回 200、消息及笔记没有重复。Windows 关闭测试服务时处理本轮进程树，避免虚拟环境启动器的子进程残留。

原因：分离包名与数据目录，比让每次运行都猜测哪些用户数据可以删除更可靠。只有检测到服务端口已关闭，才记录断网证据。保存环境、APK 哈希、逐项结果和截图，让失败可追查；设备流程中任一失败不继续宣称整体验收成功。模拟器中途退出属于环境中断，必须保留失败记录，不能当作应用通过。

实际修复：设备截图发现系统浅色模式下，应用深色页面的状态栏仍显示深色图标。现在状态栏图标跟随应用主题，而不是仅采用启动时的系统主题；设备断言和深浅色截图共同验证。

代价与复评：设备检查比本机测试慢，检查点按顺序共享临时数据，须使用主机脚本运行。自动化编辑中文不等于输入法候选、光标或厂商系统验收；正常结束测试界面后再强制停止也不覆盖前台运行中的突然强杀。独立模拟器不代表实体手机。覆盖安装旧 APK、回复中途断流及停止操作另行验收，保留在清单中。

依据：[Compose 测试](https://developer.android.com/develop/ui/compose/testing)、[AndroidX Test 版本与依赖](https://developer.android.com/jetpack/androidx/releases/test)。使用与工程一致的 Compose BOM，测试库固定为 runner/core 1.7.0 与 ext.junit 1.3.0。

Windows 进程处理仅增加开发依赖 [psutil 7.2.2](https://pypi.org/project/psutil/7.2.2/)，不引入服务生产依赖。先取得本轮服务的父子进程对象再终止，避免按进程名误杀其他服务，也避免启动外部清理程序的延迟使短模拟回复在强停前已经完成。

## D28 让故障发生在可核对的时刻，并用历史安装包验证升级

问题：测试正常退出之后强制停止，不能证明前台突然终止也能恢复；短模拟回复可能在点击停止前完成；从 SQL 构造旧库的测试不能完全代替旧安装包覆盖升级。重复出现的模拟台词也可能让界面检查误把旧回复当作新回复。

选择：设备测试在草稿确实落库、Activity 仍为 RESUMED 时写入当前 PID 并等待。主机同时核对进程身份和系统前台 Activity，再强制停止；要求测试没有正常结束，也没有执行退出见证标记，重启后检查完整草稿和服务端消息集合。只承诺恢复已保存内容，不把尚在写入的编辑算入保证。

选择：在独立测试服务中注入可暂停的模拟模型，笔记工具提交后、第一段正文输出后暂停；通过真实停止入口取消，再发送下一条。设备检查部分正文及按钮，主机核对任务为 cancelled、笔记仅一份，并按新消息 ID 核对下一任务确实 completed。测试暂停逻辑放在 scripts 中，生产启动不会加载。

选择：从固定历史提交 `b1f27ae6d91ad444ced71ef85a80a148e66ca2e1` 导出 Android 源码，只修改 applicationId 为专用测试包并构建 schema 1 APK。旧版经真实界面准备已完成消息和离线 outbox，然后覆盖安装当前 schema 2 APK；升级过程中不清空数据、不卸载、不替换数据库。逐行核对 snapshots、outbox、conversation_requests 和已存加密连接，恢复服务后用原请求身份重试，并保存、重开新草稿。

原因：分别保留前台进程证据、部分输出证据、历史 APK 哈希与旧库内容，验收结果才能对应实际触发条件。等待旧缓存角色出现后再检查 schema，避免静态页面标题先显示、数据库还未迁移的竞态。主机读取 JSON 明确使用 UTF-8，避免 Windows 系统编码将中文测试数据误读成程序故障。

代价与复评：扩展设备检查时间更长，需先构建历史 APK；固定历史提交、调试签名和专用包验证的是本机覆盖升级，不代表正式签名、应用商店升级或全部历史版本。强制停止不是系统低内存回收或断电。没有改变业务源码；真实模型、实体手机、完整输入法和回复过程中设备断流仍需各自验证。测试框架故障同样记录为失败，不覆盖失败证据，也不把后续成功写成首轮成功。

## D29 先交付私有角色管理，修改与删除不改写旧对话

问题：项目此前只能使用两个内置角色，连续阶段偏重基础可靠性，缺少用户可操作的管理功能。角色一旦可以编辑，直接读取角色当前名称和人设会悄悄改变旧会话；物理删除又会破坏消息、笔记和固定人设的关联。

选择：按用户反馈先交付角色增删改查，个人资料作为下一步，剩余设备验收持续保留。新增角色只能由当前身份查看、编辑和删除；内置角色可见但不可改。服务端从认证身份赋予 owner_id，不接收客户端指定所有者。人设仅在所有者编辑接口返回；列表仍只提供展示资料与 editable 标志。首版能力只允许一个显式笔记开关，不接受任意工具 ID。

选择：每次保存发布不可变人设版本，并把角色名称也写入版本；会话始终引用创建时的版本。删除仅标记 deleted_at，从发现页和新建会话入口移除，不删除旧会话、草稿、消息或笔记，旧会话继续按原设定工作。被删除的 ID 不得通过 PUT 重新创建。迁移 004 只增加字段与索引，回填旧版本名称，不修改既有迁移。

选择：用客户端 UUID 定位角色，PUT 带 expected_version（0 为新建）。事务内检查所有权与当前版本；相同内容、相同基准版本的紧邻重试返回已保存版本，不再次发布；陈旧且不同的内容返回 409。Room 在 HTTP 前保存这次提交的 ID、版本和内容，失败后保持原内容，只能重试或明确重新读取已保存版本，不静默覆盖新版本。重复 DELETE 对所有者返回成功。角色列表完整拉取后在事务中替换缓存，使已删除角色真正消失；任何分页失败都保留旧缓存。

原因：数据和操作放在服务、仓库及领域接口，Compose 表单只读业务值并发出回调，同一流程可换主题或布局。固定 UUID 防止重试重复创建，版本检查防止过期表单覆盖较新修改，事务把角色资料和人设版本共同提交。提交意图复用 Room snapshots 的独立 kind，按现有连接范围隔离，不需要改变手机数据库结构。

代价与复评：角色编辑尚未点击保存时只在 ViewModel 内，不提供跨进程编辑草稿；点击保存后的待确认内容才持久化。角色修改不回写旧会话，撤销旧会话某项权限需要未来单独的会话设置。删除是产品上的移除，不是服务器数据彻底擦除；后续隐私清理另定范围。当前没有头像/背景上传、公开角色、搜索或共享，也没有服务端离线写入队列。真实模型未配置时仍显示固定模拟回复，人设与能力虽真实保存，不能声称已验证人设化 AI 回复。将来多端发布、角色恢复与公共分享需扩展冲突和审核规则。
